# Горячее исправление после сдачи (HOTFIX)

Документ на случай, если после тега `v1.3-submission` жюри (или мы сами) найдёт **блокирующую**
проблему: `make check` / `make docker-check` не проходит на их машине, неверная награда, утечка
эталона, падение генератора на допустимом конфиге. Опечатки в документах, новые идеи и «можно
лучше» — **не** блокирующие: их не трогаем до объявления результатов.

## 1. Кто следит за каналом

| Роль | Кто | Что делает |
|---|---|---|
| Дежурный по каналу организаторов (Telegram/почта формы) | Алдик | читает канал каждые 2 часа до объявления результатов; пересылает сообщение жюри в чат команды дословно, со временем получения |
| Воспроизведение | Бекназар | повторяет проблему на свежем клоне тега и в Docker (`--network none --cpus 2 --memory 4g`); пишет точную команду и вывод |
| Исправление | Ералы | ветка `hotfix/<кратко>` от тега, минимальный патч + тест‑сторож |
| Ревью и данные | Ибрагим | читает diff, проверяет, что ядро не тронуто сверх нужного и что ручные компании (`tests/fixtures/`) по‑прежнему решаются |

Решение «пересдавать или нет» принимают вместе Ералы и Бекназар после воспроизведения. Если
проблему **не удалось воспроизвести** на свежем клоне тега — отвечаем жюри точной командой и
выводом с нашей стороны (`reports/selfcheck.md`, хеши из `reports/repro_certificate.md`), код не трогаем.

## 2. Порядок действий

1. **Воспроизвести на теге, а не на рабочей ветке** (≤ 15 мин):

   ```text
   git clone https://github.com/diawx-6669/XAZAYEVA- hf && cd hf
   git checkout v1.3-submission
   make docker-check            # или make check, если жюри запускало без Docker
   ```

   Записать: ОС, архитектуру (`uname -m`), версию Docker/Python, точную команду жюри, первые и
   последние 30 строк вывода.

2. **Классифицировать** (одна строка в чат): `сборка` (Docker, колёса, базовый образ) /
   `контракт среды` / `оценщик и награда` / `данные и эталон` / `документация` / `не воспроизводится`.

3. **Ветка от тега**:

   ```text
   git checkout -b hotfix/<кратко> v1.3-submission
   ```

   Сначала тест, который падает на теге (кладём в `tests/test_hotfix_<кратко>.py`), потом минимальный патч.
   В `docs/FAILURES.md` — строка в таблицу «Уязвимости среды» (симптом, как нашли, влияние,
   исправление, тест‑сторож). Сообщение коммита начинается с `fix:`.

4. **Минимальный набор проверок перед пересдачей** (всё офлайн):

   | Проверка | Команда | Ожидаемый итог |
   |---|---|---|
   | быстрые тесты и смоук | `make quick` | `passed`, `quick smoke` |
   | полная проверка | `make check` | табло `90/90`, `check: ALL GREEN`, `docs-check … 0 mismatches` |
   | контейнер жюри | `make docker-check` | то же внутри `--network none` |
   | детерминизм не сломан | `make repro-cert` | все 20 хешей эпизодов и детерминированная часть selfcheck совпадают с тегом, если патч не трогал генератор; иначе — перегенерировать `make episodes trajectories golden` и объяснить в CHANGELOG |
   | секреты и мусор | `make prepublish` | `0 findings` |
   | готовность к тегу | `make verify-release` | `7/7 OK` |

5. **Пересдача.** Если правила хакатона разрешают обновление после дедлайна:

   ```text
   git tag -a v1.1.1-hotfix -m "hotfix: <кратко>"
   git push origin hotfix/<кратко> v1.1.1-hotfix
   ```

   Тег `v1.3-submission` **не двигаем и не удаляем** — жюри должно видеть, что было сдано в срок.
   В форму/канал отправляем: SHA нового тега, ссылку на diff `v1.3-submission...v1.1.1-hotfix`,
   строку из `FAILURES.md` и вывод `make docker-check`. Шаблон сообщения:

   > Найдена проблема: <симптом>. Воспроизводится командой <команда> на теге v1.3-submission.
   > Исправление: <одна фраза>, diff <N> строк, тест‑сторож <имя теста>. Новый тег v1.1.1-hotfix
   > (SHA <...>). `make docker-check`: 90/90, ALL GREEN. Если обновление после дедлайна не
   > разрешено — просим оценивать v1.3-submission; проблема описана в docs/FAILURES.md.

   Если правила **не разрешают** обновление — не пересдаём, а отвечаем жюри по шаблону выше
   (без «новый тег»), чтобы проблема была признана и описана нами самими.

6. **После**: слить `hotfix/*` в `main` обычным merge, не rebase; запись в `configs/CHANGELOG.md`,
   если менялась генерация.

## 3. Чего не делать

* Не переписывать историю (`push --force`), не двигать и не удалять тег `v1.3-submission`.
* Не «чинить» несколько вещей в одном hotfix: одна проблема — один тест — один коммит.
* Не менять `configs/` и формулы награды ради «красивых» чисел: это меняет эталон задним числом.
* Не отвечать жюри до воспроизведения: сначала команда и вывод, потом выводы.
