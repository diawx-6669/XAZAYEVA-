# DESIGN — устройство AuditEnv

## 1. Поток данных

1. **История** (`generator/story.py`, поток `story`): часовой пояс, базовая и иностранные
   валюты, период (3 месяца), клиенты, ежедневные курсы на рабочие дни (случайное блуждание в
   целых базисных пунктах, `Decimal`, 6 значащих цифр), счета, оплаты, возвраты и все
   отвлекающие случаи. Здесь же планируется распределение каждой оплаты.
2. **Книги** (`generator/books.py`, поток `naming` для ID): каждый документ «владеет»
   проводками с внутренними ролями (`inv_ar`, `pay_cash`, `pay_ar:<счёт>`, `pay_unapplied`,
   `pay_fx`, `fee_*`, `ref_*`, `cn_*`). Роли наружу не выходят.
3. **Сканер совпадений**: независимый решатель (`grader/validate_truth.py::solve`) запускается
   на чистой книге. Если он что‑то нашёл (случайно совпали строки счетов и т. п.), попытка
   отбрасывается и берётся следующий под‑seed `attempt+1`. Отказы пишутся в
   `provenance.rejections`. Замер на 1 000 эпизодах (4 конфига × 250 seed): 0 случайных совпадений,
   2 перегенерации из‑за того, что обязательный сценарий взаимодействия не удалось внести
   (`injection_failed`, interaction-heavy), 0 расхождений решателя с truth.
4. **Ошибки** (`episode.py::inject_errors`, поток `errors`): сначала сценарии взаимодействия
   (по алфавиту), затем независимые ошибки строго в порядке `duplicate_invoice →
   payment_allocation → fx_rate → period_cutoff`. Каждая мутация атомарна (выполняется на
   копии книги и принимается только целиком) и пишет снимки «до/после».
5. **Экспорт** (`export.py`, поток `order`): проводки по времени, ничьи по `order`; счета и
   платежи перемешаны; канонический JSON/CSV, переводы строк `\n`.

Каждое случайное решение берётся из `random.Random(sha256(f"{seed}:{stream}:{attempt}"))`;
глобального `random`, `time.time()`, `uuid4()`, `hash()` в выходных данных нет.

## 2. Инварианты (`generator/invariants.py`) и чем ломается каждый

| Инвариант | Смысл | Ломается ошибкой | Сумма нарушения |
|---|---|---|---|
| `double_entry` | Σдебет = Σкредит по книге и по каждой группе (timestamp + payment_id/invoice_id); у строки ровно одна положительная сторона; всё в базовой валюте | никогда | — |
| `completeness` | каждый счёт проведён ровно один раз (1200/4000), каждый платёж проведён, все ссылки разрешаются, строки счёта суммируются в total | никогда | — |
| `allocation` | платёж с `invoice_refs` распределяется по правилу политики (по порядку ссылок до открытого остатка), на 2400 — только платежи без ссылок | `payment_allocation` | кредит 2400 |
| `fx_conversion` | проведённая сумма документа = `round(amount × курс локальной даты)` (с previous_business_day) | `fx_rate` | \|проведено − правильно\| |
| `period` | все проводки внутри `[start, end)` по местному времени | `period_cutoff` | Dr 1200 счёта |
| `unique_billing` | нет двух действующих счетов с тем же клиентом, валютой и строками (с учётом credit note) | `duplicate_invoice` | Dr 1200 дубля |

Тест `test_error_breaks_exactly_its_invariant` проверяет для каждого типа: множество нарушенных
инвариантов = ровно `{свой}`, а сумма нарушения = `expected_amount_minor`.

Инвариант CLAUDE.md «сальдо 1200 по счёту = сумма счёта − распределённые оплаты» реализован как
часть `allocation`: ожидаемое списание 1200 считается по правилу распределения из документов и
сравнивается с проводками.

## 3. Решения (решение → альтернатива → почему)

**Канонические affected_ids.** Один ID документа, который «ошибочен»: дубль — `invoice_id`
более позднего счёта; распределение — `payment_id`; курс — `invoice_id` или `payment_id`
пересчитанного документа; cutoff — `invoice_id`. → Альтернатива: пара (оригинал, дубль) или ID
строк проводок. → Один ID однозначен, его можно вывести из открытых данных, а «какой из двух —
дубль» решается правилом «более поздний `issued_at`», опубликованным в задаче.

**Сумма — модуль искажения в базовой валюте.** → Альтернатива: сумма в валюте документа. →
Ledger целиком в базовой валюте; разные валюты нельзя сравнивать без конвертации; одна валюта
для всех типов упрощает matcher.

**Допуск по сумме ±1 минимальная единица** (`tolerance_minor` в конфиге). → Альтернатива: 0 или
процент. → Покрывает разницу округления при пересчёте другим порядком операций, но не
позволяет перебором ±k получить TP (проверено атакой `amount_bruteforce`: 1 TP + 10 FP).
Все внесённые искажения ≥ 100 ед., т. е. ≥ 100× допуска.

**Ничьи в matcher.** Максимальное паросочетание алгоритмом Куна; вопросы перебираются по
возрастанию `issue_id`, кандидаты — по возрастанию индекса вывода. → Альтернатива: жадное
сопоставление. → Жадное может отдать вывод «не тому» вопросу и занизить TP; Кун даёт максимум,
а порядок обхода делает выбор детерминированным (`test_tie_break_smallest_issue_then_index`).

**Доказательства.** 1–3 альтернативных минимальных набора ≤ 6 ID; TP требует, чтобы один набор
целиком входил в `evidence_ids`. Каждый набор независимо проверяется
`validate_truth.verify_evidence`: сумма пересчитывается **только** из записей набора. → Альтернатива:
требовать все наборы или «хотя бы один ID». → «Хотя бы один» поощряет спам, «все» требует
лишнего. Лимит 10 ID на вывод не даёт перечислить пол‑книги.

**Дата курса.** Местная календарная дата транзакции в часовом поясе компании (счёт — `issued_at`,
платёж — `timestamp`); нет курса — предыдущий рабочий день. Курс списания дебиторки при оплате —
курс даты счёта, разница — на 7900. → Альтернатива: дата UTC. → Иначе «UTC‑ловушка» была бы не
ошибкой, а правилом; вариант `fx_rate/utc_date` как раз моделирует эту путаницу.

**Порядок мутаций** фиксирован (раздел 1 п. 4). Сумма каждого вопроса — относительно состояния
перед своей мутацией. В `partial_fx_cutoff` сначала неверный курс, затем частичное
распределение: сумма fx = |Dr 1000 − правильно|, сумма распределения = кредит 2400 в том виде, как
проведён. В `duplicate_fx` сначала неверный курс оригинала, затем дубль, скопированный «как
проведён»; дубль исключается из проверки курса (иначе одно искажение считалось бы дважды).

**Цели мутаций.** fx_rate по счёту, cutoff — только для неоплаченных счетов без credit note и
возвратов; payment_allocation — только платежи, которые единственные распределяются на свои
счета. → Альтернатива: любые документы. → Иначе последствия ошибки растекаются по другим
документам и сумма перестаёт однозначно выводиться из доказательств.

**Credit note.** Документ в `invoices.jsonl` с отрицательными суммами; ссылка на отменяемый
счёт — ключ `cancels_invoice_id` **внутри каждой строки `line_items`**. Верхний уровень счёта
содержит ровно поля кейса (`doc_id, invoice_id, entity_id, issued_at, due_at, currency,
total_minor, line_items`). Проводки: Dr 4000 по строкам / Cr 1200. → Альтернативы: поле
верхнего уровня (было раньше) или ссылка в тексте `description`. → Поле верхнего уровня
нарушает перечень полей кейса; текст пришлось бы разбирать. Состав строк кейс не фиксирует,
поэтому ключ в строке — явная, проверяемая схемой ссылка. Тест:
`test_data.py::test_invoice_fields_exactly_as_in_case`.

**Выручка по строкам счёта.** Dr 1200 — на всю сумму документа в базовой валюте; Cr 4000 — по
одной строке на позицию `line_items`. Если документ в иностранной валюте, сумма в базовой
валюте делится пропорционально суммам позиций методом наибольшего остатка (ничья — ранней
позиции), так что Σ Cr 4000 = Dr 1200 точно. Правило записано в `policy.json`
(`revenue_posting`). → Альтернатива: одна строка выручки на счёт. → Так книга реалистичнее и
ближе к размерам из кейса. Наборы доказательств: основной — со строкой 1200; альтернативный —
со **всеми** строками 4000 счёта, если умещается в 6 ID (по одной строке выручки сумма не
доказывается).

**Часовые пояса** — только без летнего времени, смещения зашиты в `timeutil.py`. →
Альтернатива: `zoneinfo`. → В `python:3.11-slim` нет гарантии tzdata, а офлайн‑проверка должна
давать те же байты на любой машине.

**Курсоры** — `base64(offset ‖ HMAC(key, episode_id|table|offset)[:12])`, ключ из episode_id и
дайджеста публичных файлов. → Альтернатива: случайный секрет. → Детерминированность нужна для
побайтового replay; подделка курсора даёт лишь смещение, которое и так доступно.

**Размеры эпизодов.** Цель для train/dev/закрытых конфигов — 200–450 проводок и 30–80
документов. По умолчанию 3‑месячный период, 24–36 счетов по 3–7 позиций. Замер на 1 000
эпизодах (4 конфига × 250 seed): 204–376 проводок, 42–78 документов, 80–243 строки курсов,
0–6 ошибок. Oracle тратит 1 шаг, simple_reconcile — 11–16 из 100. → Альтернатива: верх
диапазона кейса (до 2 000 проводок). → 100 шагов по 50 строк — это до ~4 500 прочитанных
строк, но честному агенту нужен запас на `get_record`/калькулятор. Пресет `stress`
(1 753–1 993 проводки, ~400 документов) — только для проверки производительности:
simple_reconcile 55–62 шага ≈ 0,1 с. Тесты: `test_episode_sizes_in_target_range`,
`test_oracle_and_simple_reconcile_fit_in_100_steps`.

**`limit > 50` → `bad_args`.** `list_records` с `limit` вне 1–50 (51, 1000, 0, не int, bool)
возвращает `{"error": {"code": "bad_args"}}` и **тратит шаг**. Молча обрезать до 50 мы не
стали. → Альтернатива: обрезать до 50. → Тихая обрезка скрывает ошибку агента и делает
контракт неоднозначным. Явная ошибка соответствует правилу «неверный ввод даёт ограниченную
ошибку и расходует шаг». Тест: `test_contract.py::test_page_limit_50` (51, 1000, 0).

**Свой валидатор JSON Schema вместо пакета `jsonschema`.** `auditenv/jsonschema_lite.py`
(~160 строк) поддерживает ровно те ключевые слова, что есть в `schemas/`, а при незнакомом
ключевом слове падает уже при загрузке схемы, чтобы ничего не игнорировалось молча.
`integer` — только настоящий `int` (не `bool`, не `5.0`). → Альтернатива: `jsonschema`. → Он
тянет `rpds-py` — скомпилированный пакет, разный для x86_64 и arm64, поэтому колёса,
скачанные на одной машине, не ставятся в контейнер другой архитектуры. Теперь зависимости —
только `pytest` и `hypothesis` (закреплена 6.155.7: это последняя версия с чисто-питоновским
колесом, новые выходят скомпилированными). Все колёса лежат в `vendor/wheels/` и имеют тег
`*-none-any` (у `sortedcontainers` тег `py2.py3-none-any`: это тоже pure Python). Тесты:
`test_jsonschema_lite.py`.

**Режимы.** `train`: терминальная награда и P/R/F1 в `info`. `eval`: награда 0, `info={}`,
наблюдение `submit` одинаковое при любом ответе (даже неверном), итог — только в
`grader_log.jsonl`.

**Процесс агента и закрытый прогон.** Политика — отдельный процесс (`runner.py`, JSON‑lines
через stdin/stdout); среда и оценщик — в родительском. Закрытый прогон `run --seed`
генерирует эпизод **в памяти** оценщика и не пишет `grader/` на диск. Агент запускается как
`python -I -S -c <bootstrap>`: `-I` игнорирует все `PYTHON*`, user site и cwd в `sys.path`;
`-S` отключает site-packages. Его cwd — новая пустая временная папка, окружение — только
`PATH`, `TZ`, `LANG` (без соли, seed и путей к данным), а код политики импортируется из
отдельной копии пакета (только `.py`, без `schemas/`, `configs/`, `episodes/`). Оценщик
вызывает `prctl(PR_SET_DUMPABLE, 0)`: после этого его `/proc/<pid>/environ`, `mem` и `fd`
принадлежат root и недоступны непривилегированному агенту. → Альтернатива: отдельный
пользователь или seccomp. → Нужен root и платформенные зависимости; в контейнере жюри и так
работает непривилегированный пользователь `auditor`. Проверка — враждебная политика
`truth_hunter` (`tests/test_isolation.py`) плюс позитивный контроль, где эпизод с `grader/`
специально лежит на диске и находится. Oracle и атаки — сторона оценщика, работают
in‑process и в траектории не пишутся.

**Таймаут.** Монотонные часы (подменяемые в тестах); проверка перед каждым шагом. Ответ,
пришедший после 60 с, **не** оценивается — оценивается пустой ответ с `truncated=true`.

**Секретная соль seed для закрытых прогонов** (`AUDITENV_SEED_SALT`). Генератор открыт, поэтому
без соли агент мог бы перебрать небольшие seed, сравнить с публичным `episode_id` и
перегенерировать truth. С солью под‑seed = `sha256(f"{salt}|{seed}:{stream}:{attempt}")`. →
Альтернатива: только большие случайные seed. → Соль надёжнее и не меняет открытые эпизоды (без
соли формула прежняя). Соль не передаётся в процесс агента и не пишется в provenance (только флаг
`seed_salted`). Тесты: `test_leaks.py::test_seed_salt_blocks_seed_bruteforce`,
`test_agent_process_gets_no_salt_and_no_paths`.

**В manifest нет имени конфига**, только `config_hash` и `config_version`. → Альтернатива: имя
конфига. → Имя `clean-only` прямо подсказывало бы «книга чистая».

**Экспериментальная награда.** TP засчитывается, только если все ID сработавшего набора
доказательств были первичными ключами записей, реально возвращённых агенту (`row_id`, `doc_id`,
`fx_id`, `policy`). Показывается отдельной колонкой, общая награда не меняется.

## 4. Политики

| Политика | Что делает |
|---|---|
| `random_explorer` | фиксированный seed, случайные (в основном корректные) вызовы, затем пустой submit |
| `simple_reconcile` | честный скриптовый аудитор и демо: читает всё постранично и ищет 4 типа (слепые зоны — в `docs/FAILURES.md`) |
| `flag_all` | обвиняет 30 документов, чередуя типы |
| `oracle` | только для оценщика: правильные выводы с первым набором доказательств за 1 шаг |
| `attacks.py` | twins, type/amount brute force, guess_ids, evidence_spam, junk_explanation, persuasive_wrong, wrong_currency, all_types_all_docs, empty |
