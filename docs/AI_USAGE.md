# Как мы использовали ИИ (честно)

Код этого репозитория в основном написан ИИ‑ассистентом **Claude Code** (Anthropic) по нашему
техническому заданию. Решения, проверка и ответственность за результат — на команде. Ниже —
что именно делал ИИ, что делали люди и какие ошибки ИИ поймали тесты и ревью. Источник — история
`git log` и `docs/FAILURES.md`; в коммитах ИИ стоит строка `Co-Authored-By: Claude`.

## 1. Что писал ИИ

* Почти весь код `auditenv/` (генератор, среда, оценщик, политики, runner, selfcheck, CLI), тесты
  в `tests/`, большая часть документов `docs/` и отчётов `reports/` — по этапам из `CLAUDE.md`.
* Инструменты проверки вокруг ядра: независимый проверяльщик `tools/verify_independent.py`,
  мутационное тестирование `tools/mutation_test.py`, автопоиск эксплойтов, эксперименты E6/E6 v2,
  инструменты раунда 4 (`tools/`, `docs/ROUND4_IDEAS.md`).
* Черновики текстов (README, памятки, формулировки для формы) — люди вычитывали и правили.

## 3. Ошибки ИИ, которые поймали тесты и ревью

| Ошибка ИИ | Как поймали | Чем закрыто |
|---|---|---|
| Работа в ветке, созданной **не от `main`** (ветка по умолчанию на GitHub устарела): изменения ложились на старый код | ревью слияния человеком | правило «только `git checkout -B <ветка> origin/main`» в задании каждого раунда |
| Утечка seed, путей и соли через `ps` / `/proc/<pid>/cmdline` оценщика: 15/15 закрытых эпизодов с наградой 1.0 | симуляция жюри Бекназара (`jury_sim/attack_isolation.py`) | `FAILURES.md` п. 15, `tests/test_conceal.py`; после исправления 0/20 |
| Зависимость `jsonschema` тянула `referencing` → `rpds-py` (Rust‑расширение): офлайн‑сборка могла не собраться | ревью сборки | собственный валидатор `auditenv/jsonschema_lite.py`, колёса только `*-none-any` (`FAILURES.md` п. 7) |
| Лишнее поле `cancels_invoice_id` на верхнем уровне счёта (в кейсе его нет) | сверка схем с текстом кейса | схема = ровно поля кейса (`FAILURES.md` п. 6, `test_guards.py`) |
| Имя конфига `config_name` в `manifest.json` выдавало «чистая книга» | ревью наблюдения | `FAILURES.md` п. 2 |
| Перебор seed без соли восстанавливал эталон | «думали как атакующий» | соль `AUDITENV_SEED_SALT` (`FAILURES.md` п. 1) |
| Неверный `submit` не завершал эпизод — бесплатное зондирование формата | ревью контракта по кейсу | `FAILURES.md` п. 8 |
| Допуск `tolerance_minor` из конфига молча игнорировался | ревью | `FAILURES.md` п. 9 |
| Суммы сценария `partial_fx_cutoff` зависели друг от друга | ревью | `FAILURES.md` п. 10 |
| Падение генератора на конфиге с одним клиентом | hypothesis‑fuzz конфигов | `FAILURES.md` п. 11 |
| Зависший агент на чистой книге получал больше честного | симуляция жюри (`jury_sim/contract_check.py`) | `FAILURES.md` п. 16 |
| Отрицательная сумма в одном выводе обнуляла весь ответ (−1) | симуляция жюри (`jury_sim/reward_attacks.py`) | `FAILURES.md` п. 17 |
| Тесты оценщика пропускали 3 из 23 намеренных мутаций (M05, M08, M18) | `make mutation` | тесты `tests/test_mutation_kills.py`, теперь 23/23 |

Вывод, который мы сделали: самые опасные ошибки ИИ (утечка через `ps`, «зависание выгоднее
честного ответа») нашли **люди, которые атаковали систему извне** и не читали её код. Поэтому
независимые проверки (`jury_sim/`, `tools/verify_independent.py`, ручные компании) у нас написаны
так, чтобы не импортировать `auditenv`.

## 4. Чего ИИ не делал

* Не выбирал кейс и не решал, что сдавать; не сливал ветки в `main` без ревью человека.
* Не имел доступа к закрытым эпизодам жюри и к их соли.
* Не обучал модели: в проекте нет обучения весов (см. `docs/LIMITATIONS.md`).
