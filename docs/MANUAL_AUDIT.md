# Ручной аудит: проверка эталона калькулятором (для не‑программистов)

**Зачем.** Код проверяет код (независимый проверяльщик, provenance, линтер), но жюри важно, что
эталон описывает **реальное** расхождение и что его можно подтвердить **только по доказательствам**.
Ручной аудит — третья, человеческая линия проверки. Нужны: Google Таблицы и калькулятор. Время:
около 30–40 минут на эпизод.

## Правила, которые нужно знать (из `policy.csv`)

* **Суммы.** `*_minor` — целые «копейки». Рядом есть колонка в обычных единицах (`total`, `amount`,
  `debit`, `credit`). Знаки после запятой: KZT/USD/EUR — 2, JPY — 0, KWD — 3 (`currency_exponents`).
* **Курс.** `rate` = сколько единиц базовой валюты за 1 единицу иностранной. Берётся курс **даты
  документа по местному времени компании** (колонка `local_time`). Если в этот день курса нет
  (суббота/воскресенье или праздник из `fx_holidays` в `policy.csv`) — курс **предыдущего рабочего дня**.
* **Пересчёт.** сумма в базе = сумма документа × курс, округление до копейки по правилу
  «половина — к чётному» (на практике: обычное округление; спорно только ровно .5).
* **Период.** Документ относится к периоду, если его **местная** дата внутри
  `[period_boundary.start, period_boundary.end)`. Время вида `…+00:00` — это UTC: переведите в
  местное (колонка `local_time` уже переведена).

## Порядок работы по каждой ошибке (`issues.csv`)

1. Возьмите строку `issues.csv`: тип, ID, сумма эталона (`expected_amount`), наборы доказательств.
2. Откройте в `evidence.csv` строки с этим `issue_id` и `evidence_set = 1`. **Пользуйтесь только
   ими** — не смотрите в другие записи. Это и есть проверка «доказательств достаточно».
3. Пересчитайте сумму калькулятором по правилу своего типа:

| Тип | Как пересчитать |
|---|---|
| `duplicate_invoice` | в наборе два счёта одного клиента с одинаковыми позициями; дубль — более поздний; сумма = проводка дубля (Dr 1200 или Cr 4000) |
| `fx_rate` | правильная сумма = сумма документа × курс из набора (дата курса — по правилу выше); ошибка = \|проведено (строка проводки из набора) − правильная\| |
| `payment_allocation` | платёж ссылается на счета (`invoice_refs`); сумма = то, что ушло **не на** эти счета: кредит 2400 (или кредит 1200 на счёт, которого нет в `invoice_refs`). В альтернативном наборе: сколько должно было уйти на счета минус сколько ушло |
| `period_cutoff` | местная дата счёта вне периода; сумма = проводка счёта (Dr 1200 или Cr 4000) |
| `vat_error` | строка «VAT 12%» должна быть = 12 % от суммы остальных строк счёта (округление half-even); сумма = \|строка НДС − правильный НДС\| |

4. Сравните с `expected_amount`: допуск — `tolerance_minor` копеек (обычно 1).
5. Заполните строку `protocol.csv`: какой набор использовали, ваш результат, совпало ли
   (`yes/no`), комментарий, ваше имя и дату. Если наборов несколько — проверьте и второй.

**Пример (папка 3, ISS‑001).** Платёж BNK‑TAM4YY на 2 660.000 KWD записан как
`2026-10-30T21:29:12+00:00` — по UTC это пятница, но по местному времени (+05:00) уже **суббота**
2026‑10‑31, 02:29. Курса на субботу нет → курс предыдущего рабочего дня, пятницы 2026‑10‑30:
1 610.87. Правильно: 2 660.000 × 1 610.87 = 4 284 914.20 KZT. Проведено (дебет 1000): 4 277 652.40.
Разница: **7 261.80** = `expected_amount`. ✔ (Второй набор доказательств того же вывода вместо строки
1000 даёт строки 1200, 2400 и 7900: сложите их кредиты — получится те же 4 277 652.40.)

### Уточнения после слепой проверки 22.11

Независимый проверяющий (без доступа к коду) задал четыре вопроса. Ответы:

1. **Альтернативный набор для `payment_allocation` в иностранной валюте.** Формула «сколько должно было
   уйти на счета минус сколько ушло» верна только в базовой валюте. Для валютного платежа эталон один:
   кредит 2400, пересчитанный по курсу **платежа** (`policy.unapplied_cash`). Пересчёт по курсу счёта
   даёт другое число, и это не ошибка эталона.
2. **Дубль, скопированный «как проведён» (сценарий `duplicate_fx`).** Его сумма тоже расходится с курсом
   политики, но отдельной ошибкой `fx_rate` он **не** считается: вся его проводка уже входит в искажение
   `duplicate_invoice`. Вывод `fx_rate` по дублю — ложная тревога (так и задумано, см. `docs/DESIGN.md`).
3. **«Это не переплата».** По одному набору доказательств этого не видно. Чтобы исключить переплату,
   проверьте другие платежи по тем же счетам (`invoice_refs`): если открытого остатка хватало, деньги на
   2400 — ошибка распределения.
4. **Остаток ±0.01 на 1200 после оплаты частями** — разница округления, корректный «двойник». Допуск
   оценщика — 1 минимальная единица.
