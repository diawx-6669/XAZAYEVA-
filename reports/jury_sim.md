# Симуляция жюри: закрытая проверка AuditEnv чёрным ящиком

Дата: 2026‑11‑21. Ветка `beka-jury` от `origin/main` (57a42a2). Код симуляции лежит в `jury_sim/`.
Правило чёрного ящика: в `jury_sim/` нет ни одного `import auditenv`. Я читал только
`docs/CASE.md`, `docs/ADAPTER.md`, `docs/CONTRACT.md` и `README.md`, а CLI (`generate`, `run --policy-cmd`,
`serve`, `transform`) запускал как внешнюю программу. Формат конфига я взял из
`grader/provenance.json` сгенерированного эпизода, то есть из выходных данных, а не из кода.

**Окружение и его ограничения.** macOS (Darwin 25.6), **Python 3.13.12** (в кейсе указан 3.11;
`python3.11` на машине нет), **Docker нет**. Поэтому всё ниже проверено на хосте без root. Изоляция
Linux (`prctl`, `nobody`, `/proc`) здесь **не проверялась**: команды для её проверки в Docker даны в конце.

## 3. Парные проверки transform: 20/20

`transform --seed 5000+n`, у нечётных n с `--opaque-ids`. Для каждой пары проверено:

- truth двойника = truth оригинала через `id_map.json` (типы, суммы, все наборы доказательств);
- открытые данные двойника = оригинал через `id_map` (как мультимножества, меняются только порядок и ID);
- ID, порядок строк и `episode_id` действительно поменялись;
- ответ oracle **оригинала**, переведённый через `id_map`, получает на двойнике полную награду, и она равна награде на оригинале;
- simple_reconcile получает на двойнике те же TP/FP/FN/F1/награду.

## 5. Атаки

### 5a. Изоляция: **пробита на macOS без root** (находка №1)

`jury_sim/policies/leak_probe.py` выносит всё, что видит, через поле `explanation`. Окружение
дочернего процесса чистое (`PATH, TZ, LANG` и системная `__CF_USER_TEXT_ENCODING`), cwd пустой, писать
файлы нельзя (`EFBIG`). **Но** процесс агента имеет тот же uid, что и оценщик, и поэтому:

- `ps -o command= -p $PPID` показывает полную командную строку оценщика: `--seed 910001 --config /…/jury-clean.json --log … --trajectory-out …`;
- `ps -E -ww -p $PPID` показывает окружение оценщика, **включая `AUDITENV_SEED_SALT`**: значение совпало с настоящей солью.

`jury_sim/policies/regen_attack.py`, у которого нет доступа к файлам эталона, делает так: берёт
seed, config и соль из `ps`, запускает открытый CLI `python -m auditenv run --policy oracle … --trajectory-out /dev/stdout`
(`RLIMIT_FSIZE` на pipe не действует), вынимает ответ встроенного oracle и отправляет его как свой.
Результат: **15/15 ошибочных эпизодов, награда 1.0 = oracle**, в закрытом прогоне с солью. В режиме
`--episode-dir` атака ещё проще: путь виден в `ps`, и `grader/truth.json` читается рядом (15/15, награда 1.0).

```bash
cd jury_sim && python3 attack_isolation.py
```

Что это значит для Linux/Docker (не проверено, Docker нет):
- соль: README обещает `prctl(PR_SET_DUMPABLE,0)`, тогда `/proc/<ppid>/environ` закрыт. **Но** если оценщик запущен через обёртку (`sh -c`, `make`, `scripts/check.sh`), соль лежит в окружении *обёртки*. Обёртка dumpable и имеет тот же uid `auditor` → `/proc/<pid>/environ` читается;
- `/proc/<ppid>/cmdline` читается всегда, даже у non‑dumpable процесса, поэтому **seed и путь конфига видны** и в Linux. Кейс прямо требует, чтобы seed не утекал;
- в образе агент работает тем же `auditor`, что и оценщик (так написано в ADAPTER.md). Значит, при `--episode-dir` с `grader/` на диске эталон читается по пути из cmdline.

## 6. Контракт (раздел 10): 20/20

`jury_sim/contract_check.py` (через `serve` и `run`): форма reset (`task, manifest, policy_summary, steps_remaining=100`)
и step (5 полей, наблюдение только `result|error` + `steps_remaining`, награда по ходу 0); лимит 50, а
`limit` 51, 0 и `"50"` дают `bad_args`; полный обход курсором совпадает со счётчиками manifest
во всех 4 таблицах, без повторов, курсоры стабильны; плохие курсоры; неизвестный tool и ID, ID из другой
таблицы, doc_id строки ledger, таблицы `truth` и `../grader/truth` — каждая ошибка тратит шаг;
кривые args; калькулятор (`__import__`, lambda, имена, `**`, `9**9**9`, `1/0`, 201+ символов, 11 уровней, `1e999999999`, списки и строки дают `calc_error`, 10 уровней работают);
100 шагов → `truncated`, награда 0.8 на чистой; submit на 100‑м шаге принят; шаг после конца даёт
`episode_over` и итог не меняется; неверный submit → −1, агент видит только `{"submitted": true}`;
eval через `serve` и через `run`: награда 0 и `info={}`; тайм‑аут → `policy_unresponsive`; не‑JSON
строка → `unknown_tool`; reset изолирует состояние.

## Команды для Docker (проверить находки 1–2 там, где есть Docker)

Внутри образа, оценщик напрямую:

```bash
docker run --rm --network none -e AUDITENV_SEED_SALT=s3cret -v "$PWD/jury_sim:/app/jury_sim:ro" auditenv python -m auditenv run --policy-cmd "python3 /app/jury_sim/policies/regen_attack.py" --seed 920001 --config /app/jury_sim/configs/jury-interact.json --mode train --log /tmp/l.jsonl
```

То же через обёртку‑оболочку (соль в окружении `sh`):

```bash
docker run --rm --network none -e AUDITENV_SEED_SALT=s3cret -v "$PWD/jury_sim:/app/jury_sim:ro" auditenv sh -c 'python -m auditenv run --policy-cmd "python3 /app/jury_sim/policies/leak_probe.py" --seed 920001 --config /app/jury_sim/configs/jury-interact.json --log /tmp/l.jsonl --trajectory-out /dev/stdout'
```

В `leak_probe` ищите `salt_visible_in_parent_env`, а в Linux‑версии нужно дополнительно читать `/proc/*/environ` и `/proc/$PPID/cmdline`.
Пути `/app/...` — предположение о раскладке образа: поправьте под `WORKDIR` из Dockerfile.
